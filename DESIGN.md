# DESIGN

## What did you eventually understand about these documents that you did not understand on day one?
On day one, I read the partial README and saw the PDFs in the document, and I understood we have initially extracted the PDF as the autodraft schema. Then I directly went to the Sarvam AI and, inside Document Intelligence, I started building my schema similar to the autodraft. Then, after 5-7 examples (Different file name PDF examples), I realize the documents look similar but are encoded with very different logic. I am focusing on recognizing the semantic pattern. From the erp.py file, I learn the totals are not enough. ERP also checks structure and values. Then some values are only valid if they match against master data (if not real match, then the correct answer is to leave blank). I also learned that many of the documents are intentionally ambiguous. The task is not about distinguishing between real payable and non-payable. The biggest shift was realizing that the problem is not what the numbers in the PDF are, but what this document is as an accounting record. That mental model changed my mind to solve this engineering challenge.  

## When your system meets a document unlike any it has seen, what does it actually do — and why does that generalise instead of guessing?
Rather than detecting invoice type, my system extracts the semantic components corresponding to the schema fields. I understand the accounting structure (i.e. (supplier, dates, totals), (quantity × price + discount + tax)) and this structure is universal across payables. It validates against the schema, it asks: "Is this value present on the document?" and "Does it belong in this schema field?" If the answer to either is no, it leaves the field empty or moves to the correct field. For lookup, I come up with rule-based master data resolution. It matches suppliers,  buyers, payment terms, PO numbers and tax codes against master files using deterministic matching. If nothing matches, it leaves the code empty (it does not guess). If a document lacks required information, then it marks the document as declined and also inserts the reason. Generalisation works because the schema is the contract. The ERP always consumes the same fields in the same way. Unknown document types don't matter; what matters is faithful extraction of the structure the ERP knows how to book. Every novel document is just a different way to express the same accounting primitives.

## Was there a document you concluded could not be solved the way the others were? If so, which, and how did you know?
Yes. Some documents were not actually solvable in a systems way. They looks like payables, but the information needed to build a correct record was missing or unclear. For example, a document might have a total but not enough evidence for the tax, the line items, or the matching supplier data  (No problem if reasoning is "on", But it's not part of our challenge.). In those cases, the page did not contain the truth needed to reconstruct the payable faithfully. The challenge rules say I must not invent numbers or codes. If a value is not on the document, or cannot be matched to a real master record, we should not guess (as discussed in question 2). So the right response was to identify that it was not a valid payable and decline with reason. I knew it was impossible when the only way to “solve” it was to make up missing facts or assume meaning that the document did not provide...
